CASE-01 · Incident response & vulnerability remediation SOCVuln Mgmt Kali · Nessus · Velociraptor

Nessus triage and a Linux persistence hunt

Final report: turned a Nessus scan into tracked tickets, ranked the medium findings, then investigated a Kali host with Velociraptor.

What I did

  • Fixed T-6 by enabling the EnableCertPaddingCheck registry value, then rescanned to confirm zero critical and zero high findings on that host.
  • For the end-of-life server, documented why patching was impossible and proposed isolation, strict firewall rules, disabled services and SIEM/EDR monitoring until the workload migrates.
  • Recorded a resolution timeline from scan discovery and noted that a real SOC needs automatic ticket timestamps to measure MTTR.
  • Planned next steps for the failed credentialed scan: check scanner permissions, SSH and firewall rules, Nessus logs, and fall back to an uncredentialed scan for partial visibility.

Top 5 medium findings, by priority

  1. MS13-036 Four kernel CVEs (race conditions, font parsing, NTFS null deref) lead to kernel privilege escalation.
  2. MS15-063 DLL planting via LoadLibrary grants full admin, but needs plant + trigger.
  3. MS12-033 Partition Manager EoP; serious but less documented.
  4. MS13-077 Service Control Manager EoP; vague advisory, no clear exploit chain.
  5. MS14-019 Needs a user to run a crafted .bat/.cmd and gives no privilege gain.

Host investigation findings

Root crontab persistence

@reboot /usr/sbin/shutdown +360 in root's crontab, not part of a default Kali build. Recommended removal, a sweep of /etc/cron.d and all user crontabs, a review of auth.log, and rotating sudo credentials.

Anti-forensics in shell history

~/.zsh_history opened with sudo crontab -e followed by history -c: someone edited the scheduler and then cleared history to cover it.

Hidden file ruled out

Found .bashrc.original, a pattern used to hide injected payloads. Diffed it against the live .bashrc: only cosmetic aliases and prompt changes.

No rogue accounts

Manual review of /etc/passwd (UID ≥ 1000) and /etc/shadow, cross-checked with Velociraptor's Linux.Sys.Users and Linux.Sys.LastUserLogin artifacts.

CASE-02 · Information security plan GRC Team of 4 · v1.0 → v4.0

SnowBe Online security plan

A security plan for a fictional online retailer with a laid-back culture, universal employee access, neglected patches and stored credit cards.

Our team turned a consultant's findings into a plan of 14 policies and 3 standards/procedures, mapped to NIST SP 800-53 access control (AC) families and to PCI DSS because SnowBe stores cardholder data.

  • Replaced "most employees had universal access" with RBAC network segmentation (AC-3) and least privilege (AC-6).
  • Covered remote access for 30 VPN laptops (AC-17), device lock and session termination (AC-11/12), information flow (AC-4) and information sharing (AC-21).
  • Defined roles, an exceptions process with compensating controls, and a version history across four revisions.

My part
Researched and wrote the introduction and definitions sections, and wrote the plan's password standard and procedure (CASE-03).

CASE-03 · Password standard & procedure GRCIT Support Sole author · Oct 2025

Password standard and password procedure

Two companion documents for SnowBe: the standard sets the technical rules, the procedure tells people and admins how to follow them.

The split matters. A standard says what a compliant password is; a procedure says what an employee does on day one and what a help desk technician does when someone is locked out.

  • Assigned responsibilities from CISO (sets parameters) to IT director (deploys enforcement tools) to sysadmins (configure OS, apps and domain controllers).
  • Required admins to verify a user's identity before any reset and to issue temporary credentials that must be changed at first login.
  • Required audit logging when a reset runs, so the ISO can review it.

CASE-04 · Threat modeling across the policy set GRCVuln Mgmt STRIDE · NIST SSDF · CMMC

Shifting security left: threat modeling in SDLC, maturity and policy

A written analysis of where threat modeling fits in SnowBe's System Development Lifecycle, Security Maturity and Patch Management policies.

  • Design: data flow diagrams and STRIDE expose trust boundaries before code is written.
  • Build and test: the model drives targeted controls (input validation against XSS and SQL injection) and points pen testing at the high-risk paths instead of generic scans.
  • Maturity: with BSIMM or OWASP SAMM, threat modeling grows from high-risk projects only to a mandatory design gate, then into CI/CD.
  • Policy: policy says what must be protected; the threat model shows how and where, and feeds the incident playbooks.

CASE-05 · Small-office network build IT Support Final project · Dec 2024 · 24 hrs logged

Network implementation for Marconi Law Firm

Scoped, priced, addressed and configured the network for a 10-person law office in Orlando, delivered as a client report and pitch.

  • Specified and priced 28 nodes: 10 laptops, 10 VoIP phones, router, rack server with RAID 5, 48-port PoE switch, 2 Wi-Fi 6E access points, printer, conference phone and smart TV.
  • Designed the addressing plan: a /24 with reserved ranges for computers (.1–30), VoIP (.31–60), network backbone (.80–90), WAPs (.90–100) and shared devices (.100–120), plus a static IP for every node.
  • Configured Windows Server: 10 user accounts, Attorneys / Accounting / Administrative groups, and departmental shared folders with permissions.
  • Troubleshot "user does not have privileges" errors on the shares; the causes were the firewall and overlapping share permissions.
  • Placed every device on the floor plan and kept timesheets and weekly status reports across four milestones.

CASE-06 · Infrastructure lab manual IT Support 34-page guide · 3 milestones

Linux and Windows Server build guide

A step-by-step manual I wrote so someone else could rebuild the environment: containers, cross-platform file sharing, Active Directory and load balancing.

  • Docker: installed Docker on Ubuntu and deployed the Mayan EDMS document system with Docker Compose; documented its OCR import, workflow and audit trail features.
  • Samba: renamed the host with nmtui, configured smb.conf, created the share and user, and verified a file written from Windows appeared on Ubuntu.
  • Windows Server: ran Sysprep on cloned VMs, set static IPs on two NICs, installed IIS, and promoted a domain controller in a new AD forest.
  • High availability: built a two-node Network Load Balancing cluster in multicast mode.
